## 1. Core Operating Philosophy

You are pair programming on **CARE (Context-Aware Reasoning & Execution)**, a project for the **NIMBUS Hackathon 2026**.

CARE is a **control plane for AI agents** that solves the gap between tool-level execution success and intent-level correctness. As an AI assistant implementing this system, you must embody the exact principles this project advocates:
- **Never perform blind mutations.**
- **Preserve frozen interface contracts.**
- **Adhere to the Plan $\to$ Policy $\to$ Execute $\to$ Verify $\to$ Recover loop.**

---

## 2. Invariant Rules (The Golden Constraints)

When creating, editing, or refactoring code in this repository, you **MUST NEVER**:

1. **NEVER modify frozen contract schemas without team consent:**  
   The schemas in `src/schemas/` (`intent.py`, `plan.py`, `journal.py`, `policy.py`) are locked as of 9:45 PM. Do NOT alter field names, add required fields without defaults, or delete fields.
2. **NEVER give the LLM direct mutation authority:**
   The conversational agent is provided only with discovery and proposal schemas. FastMCP mutation tools require an exact persisted action, its active write-ahead record, and a one-time dispatch capability generated by `src/executor/runner.py`; `plan_id` and `action_hash` alone never authorize a write.
3. **NEVER bypass Plan-Before-Policy:**  
   The Policy Engine must **always** evaluate the concrete candidate actions generated by the dry run, **never** the raw natural-language prompt alone.
4. **NEVER use LLM confidence as an authorization gate:**  
   `intent_confidence` is qualitative (`low`, `medium`, `high`). It is an informational metric, **not** an authorization threshold.
5. **NEVER break canonical hashing rules or omit replay protection:**  
   `action_hash` must always be computed via SHA-256 on canonical JSON (`sort_keys=True`, `separators=(',', ':')`, stripping mutable fields like `status`). The executor must enforce that `plan_id` is single-use and transitions to `executing` immediately to prevent replay.
6. **NEVER introduce arbitrary constraint types:**  
   Only four constraint types are permitted in the contract:
   - `preserve_items`
   - `max_affected`
   - `no_destructive_actions`
   - `expected_state_equals_actual_state`
7. **NEVER omit write-ahead action logging:**  
   `before_state` must be recorded in SQLite before a tool is dispatched (`status="executing"`). `after_state` must be recorded after return (`status="done"`). If interrupted mid-flight, reconcile external state before recovery.
8. **NEVER bypass drift checks during compensation:**  
   Before running a saga rollback, the system **must** assert `current_state == journaled after_state`. If drift is detected, abort rollback and flag for human review.

## 4. Coding Standards & Conventions

### Python 3.11+ Standards
- Use modern Python typing (`list[str]`, `dict[str, Any]`, `X | None`).
- Use **Pydantic v2** (`BaseModel`, `Field(default_factory=...)`).
- Use asynchronous SQLite (`aiosqlite`) or standard `sqlite3` with `PRAGMA journal_mode = WAL;`.
- Avoid heavy, bloated dependencies. Keep runtime lean for hackathon execution.

### Error Handling Standard
Never silently catch or suppress exceptions when executing tools, writing journal records, or verifying drift:
```python
# GOOD: Explicit error tracking in Journal
try:
    result = await tool.execute(params)
    await journal.record_success(action_id, after_state=result)
except Exception as exc:
    await journal.record_failure(action_id, error=str(exc))
    raise ExecutionFailedException(f"Action {action_id} failed: {exc}")
```

### Deterministic Test Assertions
Always accompany new features with unit or integration tests in `tests/`:
```bash
# Run test suite
pytest tests/ -v
```

- Focus on `src/intent/parser.py` and `src/policy/engine.py`.

### If implementing Member B (Tools & MCP):
- Focus on `src/mcp/server.py` and `src/mcp/domains/calendar_module.py` & `tickets_module.py`.
- Ensure state-changing tools inspect `plan_id` and `action_hash`.
- Provide helper methods to inject simulated failures (`simulate_failure=True`) for demo Beat 4.

### If implementing Member C (Journal & Recovery):
- Focus on `src/journal/db.py`, `src/integrity/hasher.py`, and `src/recovery/drift_detector.py`.
- Write-ahead order:
  1. Write `status="executing"` with `before_state`.
  2. Execute action.
  3. Write `status="done"` with `after_state` or `status="failed"` with `error`.
- Ensure `DriftDetector.check(resource_id, expected_after_state)` triggers an alert when unequal.

### If implementing Member D (UI & Demo Runner):
- Focus on `ui/app.py` and `demo/run_beat.py`.
- Ensure the 4 demo beats can be executed via clean CLI flags:
  `python demo/run_beat.py --beat 1`
